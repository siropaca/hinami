# 最先端の事例と手法の調査 (2026-11-28)

> **状態: 提案 (作り手の判断待ち)**。4 つの角度でエージェントに調べさせ、施策の案を作り、プロダクトと技術の 2 つの目でレビューして組み直した。決まったものは該当する docs に反映する。

## 結論

軸は「**残すのは一瞬、選ぶときに記録が答える**」。次の一皿・一杯を選ぶとき、自分の記録が答えてくれる。これが日記アプリ全般にはない、食と酒の記録帳ならではの価値になる。

| 施策                                      | 中身                                                                                               | 今の決まりとの関係                                                               | いつ                 |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------- |
| 1. 撮ったら残る                           | シャッターだけで記録になる。確認カードは直したいときだけ開く                                       | 「＋ → シャッター → 残す」の 3 タップを変える (こちらのほうが良いのでは、の提案) | PHASE 1 で採って測る |
| 2. 酒は銘柄まで残る                       | ラベルから銘柄・蔵・都道府県の候補を出し、タップで確かめる                                         | 「名前はメモの候補にする」を、酒に限って改める                                   | PHASE 1 で確かめる   |
| 3. 記録が答える: 前回のこの店と、週の帳面 | 店が決まったら、前にそこで食べたもの・飲んだ酒と自分の順位を出す。週の終わりに、その週の皿を並べる | 「食事の詳細に順位を出さない」を改める                                           | PHASE 1 で採る       |

作り手に決めてほしいこと: この軸と 3 つで進めてよいか。施策ごとに、今の決まりを変えてよいか。

## 施策

### 1. 撮ったら残る

- **中身**: シャッターを押した時点で記録になる。種類と店は保存のあとに付く。確認カードは、トーストの「直す」や食事の詳細から、直したいときだけ開く。ロック画面のコントロール (決めたこと) と合わせると、「コントロール → シャッター」で終わる
- **なぜ**: 記録漏れは、レビューで PHASE 1 を落とす最大の理由とされた。標準のカメラより手数が多いことが漏れの一因と見る (推測)。今の決まりでも、直さずに残すことはできる ([`../../ux/recording.md`](../../ux/recording.md))。前のレビューも、種類の判定は保存のあとに付く形を標準にするよう勧めていた
- **決めること**: 確かめる前の食事のシェア。確かめるまでは「自分だけ」にするのが安全 (見ていない写真が友だちに出ない)
- **PHASE 1 で測る**: 撮ってから保存までの秒数、記録漏れの率 (端末の写真と突き合わせる)、あとから直した率

### 2. 酒は銘柄まで残る

- **中身**: ラベルから銘柄・蔵・都道府県の候補を出し、タップで確かめる。外れたらメモに残す。名前を、メモの候補ではなく、銘柄として持つ (酒に限る)
- **なぜ**: 対象ユーザーがいちばん欲しいのは銘柄 (前のレビューの 3 章、作り手の声の「あの日本酒なんだっけ」)。銘柄が分かると、前回のこの店、蔵や都道府県の広がりの実績 (飲む量ではなく広がりで数える)、姉妹アプリ、協賛ラリーにつながる。Vivino はラベルの読み取りで伸び (35 億回超)、さけのわは銘柄の味の傾向を出している
- **前提とリスク**: 銘柄の一覧は、さけのわの公開 API が候補 (レビューで、無料・商用可・帰属の表示が条件と確かめた。運営の判断で止められる)。日本酒のラベルは縦書きや毛筆が多く、端末の文字認識は苦手。外部の AI が要る見込み
- **PHASE 1 で確かめる**: ラベル 30 枚で、端末の文字認識と外部の AI を比べる

### 3. 記録が答える: 前回のこの店と、週の帳面

- **前回のこの店**: 店が決まったら、食事中のホームと食事の詳細に、前にそこで食べたもの・飲んだ酒と、その種類の自分の順位を出す。次に何を頼むかに効く。確認カードには足さない (施策 1 を軽く保つため)
- **週の帳面**: 週の終わりに、その週に残した皿を並べる。件数、空白の日、目標は出さない。記録がない週は何も出さない。通知では出さない。週か月かは、PHASE 1 の件数を見て決める
- **なぜ**: 人は日常を後で見返す楽しさを低く見積もる (Zhang ら 2014、査読)。週の始まりは新しいことを始める意欲が高まる (Dai ら 2014、査読)。週の帳面は、PHASE 1 の 3〜4 週目に実績が出にくくなる問題も補う
- **後に回すもの**: 「1 年前の今日」(PHASE 1 では 1 年前の記録がない) と、年の帳面 (年間ふりかえり)。方針だけを残す。思い出に出さない設定を持つ、量を出さない、1 枚ごとに出すものを選べる

## 技術の方針 (施策ではなく、技術の確認で決めて ADR にする)

- **種類の判定は端末を第一にする**: iOS 27 の Foundation Models は画像を受けられる (レビューで一次情報を確かめた)。上位 3 つを出し、1 タップで直せる形にする。動かない端末では、Vision の画像分類、その店で前に選んだ種類、同意を取った外部の AI、手で選ぶ、の順に頼る。対応する iPhone は今の利用者の 4 割強 (15 Pro、16 以降など)
  - 確かめ方: 作り手の過去の食の写真 200 枚に正解を付け、上位 1 つ・上位 3 つの正答率、待ち時間 (中央値と 95% 値)、発熱を測る。外部の AI とも比べる。採る基準の例は、上位 3 つで 9 割、95% 値で 2 秒
  - 今想定している Jev を置き換える可能性がある。外部の AI に写真を送らないのが既定になり、電波がなくても種類が付く。ただし、写真は同期と友だちのためにサーバーに置くので、「写真を外に出さない」とは言えない
- **店は MapKit の Place ID で持つ**: 保存の制限を受けない。1 つの店に複数の ID が付くことがあるので、自前の店の ID にまとめる。日本の飲食店の網羅度を確かめる
- **データの持ち方**: 記録に、種類の ID、種類の一覧とモデルの版、確からしさを持たせる。時刻は UTC と現地の時差。端末の DB を正にし、オフラインで動く
- **写真の位置**: HINAMI のカメラで撮った写真には位置を付ける (expo-image-picker のカメラは付けない)。友だちに渡す前に EXIF の位置を消す
- **審査**: 限定テストの TestFlight (外部テスト) にも審査がある。その前に Sign in with Apple を足すほうが安全

- 記録の手間を減らす最前線は、アプリを開く前に記録を始められる OS の入口 (ロック画面のコントロールなど)
- AI は、端末の中で動かしてプライバシーと両立させるのが今の流れ (Apple の Foundation Models、Day One)
- 続けてもらう力は、記録が返ってくること (思い出、節目のまとめ、順位) から生まれている。途切れた連続日数を見せると、行動そのものから離れやすい (研究)
- 記録は無料のまま、見返しの深さで課金する型がある (Letterboxd。ただし収益化は弱いとも評される)。無料だったものを有料に移すと反発される (Vivino、Strava、Mapstr)
- 報告の数字や仕様は、エージェントが調べたもの。iOS の仕様の多くは技術のレビューで一次情報と照らした ([`platform.md`](platform.md) の「レビューで確かめたこと」)。ほかは確かめていない
