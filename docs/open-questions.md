## UX (画面の流れ)

1. 種類の一覧そのもの (どの種類を、どの段に入れるか)。アプリを作るときに作り、境目 (「つけ麺」をラーメンと分けるか、など) は作り手が見る。持ち方と作り方は決めた ([`ux/kinds.md`](ux/kinds.md))
2. つながる (SNS) の中身の残り。スタンプの種類 (見た目のデザインと一緒に決める)、運営からのお知らせの中身 (宣伝を含むか。含むなら通知のお願いの画面に別の同意を置く。[`ux/onboarding.md`](ux/onboarding.md)) ([`ux/connect.md`](ux/connect.md))
3. 実績のタブの残り。スタンプの種類 (一旦の形はあり、あとで詰める) ([`ux/achievements.md`](ux/achievements.md))

## 技術 (未確認)

- 画像判定の AI は TypeSafe AI の Jev を想定 (要確認)。端末内では動かず写真を外部に送るため、送る前に位置情報を消す。画像入力はまだ実験扱い。電波のない場所では判定を後回しにする。種類 (ラーメン、日本酒など) の判定は、Jev の画像認識で足りると作り手は見ている。写真から銘柄や品名の文字を読めるか (メモの候補に使う) は要確認
- 実績を運営の管理画面から足すには、実績の定義をアプリの外 (サーバー) に置く必要がある。サーバーの構成はまだ決めていない
- つながる機能で、投稿前に不適切なものを弾く仕組み (App Store の審査ガイドライン 1.2)。メッセージの言葉や写真をどう判定するかは未決
- アカウントがないと使えない作りにする。App Store の審査ガイドライン 5.1.1 は「アカウントが中心の機能がないアプリは、ログインなしで使えるようにする」としている。HINAMI は記録をサーバーに置き、友だちの機能もあるので、アカウントが中心の機能と言える見込みだが、審査で通るかは確かめる ([`ux/onboarding.md`](ux/onboarding.md))
- ログインは、まずは Google だけにする。App Store の審査ガイドライン 4.8 は、Google などのログインでアカウントを作るアプリに、同等のログイン (名前とメールだけを集め、メールを隠せて、広告のための追跡をしないもの。Sign in with Apple が当てはまる) も出すことを求めている。作り手だけで使う PHASE 1 は Google だけでよいが、App Store に出す前に足す ([`ux/onboarding.md`](ux/onboarding.md))
- Web のプロトタイプでは、iOS Safari が写真の位置情報を消す場合がある ([WebKit bug 257534](https://bugs.webkit.org/show_bug.cgi?id=257534))。写真から店を出す流れは Web では試せない恐れがある

## デザイン

1. 世界観「夜の帳面」で進めてよいか
2. 写真は自分の写真で作り込むか、生成した写真で仮に組むか
3. 明るい (生成り背景) 版も用意するか、墨色 1 本に絞るか
4. 残りの画面 (地図、年間ふりかえり、つながる) を同じ世界観で起こす
5. 食事の詳細の写真の見せ方 (大きさ、並べ方)。UX では出す要素だけを決めた ([`ux/history.md`](ux/history.md))
